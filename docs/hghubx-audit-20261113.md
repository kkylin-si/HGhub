## 不能直接覆盖的功能冲突

1. **磁盘缓存与 Linux 媒体代理。** 当前新增功能通过 `src/playbackCache.ts`、Rust media_cache/media_download、Range/206 响应支持 MP4 分块复用、磁盘预取、播放请求优先及音轨/字幕缓存。HGhubX 只有分片/Key 内存缓存；`src-tauri/src/linux_http.rs:52` 明确丢弃全部请求头，`:70` 调用不接收 Range 的 media::handle；`media.rs:368` 的协议入口也没有 Range 参数。直接选 HGhubX 对应实现会失去这组新增能力。保留需要把磁盘缓存接入 HGhubX 媒体通道，并适配 Linux HTTP 的 Range、状态码及响应头，不能只选一边文件。
2. **严格模式/CIDR 与代理兼容。** `net.rs:309` 将任意代理环境变量或系统代理启用视为有代理；`:329` 在这个条件下跳过本地 DNS 解析、地址检查与固定，严格模式也如此。URL 字面量检查仍然存在，不能描述成所有检查都关闭。特别是 NO_PROXY 或系统绕过规则让请求实际直连时，仍可能进入跳过 DNS 校验的路径，这是静态推断的风险，尚未动态复现。HGhubX 没有本地新增的 CIDR 设置命令。直接覆盖会改变既有严格模式语义并丢失例外设置；需要决定安全保证与代理解析兼容之间的策略。
3. **独立观看进度。** 当前 Feed 使用 useWatchProgress 避免旧播放器覆盖新进度，HGhubX 使用自己的 Feed/store 实现，未提供这个 hook。直接覆盖会丢掉本地进度竞态修复；需要把 hook 接入它的新 Feed 生命周期。

## 其他迁移差异

- HGhubX 的 session.rs:65/114 使用普通读取/写入，没有本地后来增加的 Unix 0700/0600 收紧逻辑。直接覆盖可能使新会话文件权限退回依赖 umask。
- Linux 代理仅监听 127.0.0.1:17650，但没有随机访问凭据，返回通配 CORS，每连接新建线程且没有并发上限。它与“代理存在即跳过 DNS 检查”叠加会扩大风险。未在浏览器中验证利用，浏览器私网访问策略也会影响可达性。
- 当前 native/android、native/ios 是独立原生客户端；HGhubX 没有这两个目录，移动端通过 Tauri 生成。全部采用 HGhubX CI 后，原生目录若保留将不再由这些 CI 构建。若目标是只贡献 Tauri 功能，建议不把这一整套原生客户端带进目标 PR。
- 频道/搜索、品牌/图标/版本、单一业务源以及四个工作流可以优先采用 HGhubX；当前多线路能力会因此退出。
- 合并预演发现 29 个文件冲突，包含播放器、网络、store、Settings、依赖清单、锁文件及 CI。未执行实际 merge/rebase。
